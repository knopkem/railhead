# 01: Spec-anchored test reconciliation — a fresh arbiter re-derives the failing test from the human plan prompt

**Mission:** The railhead drives unattended builds on small-context models, and its gates are the only oracle. Verify failing on a test the Implementer itself authored is a non-oracle when the test is unsatisfiable — the only anchor neither the Implementer nor its test shares is the human spec, so the railhead must bring that spec to a fresh context exactly once, apply what it decides mechanically, and cap the blast radius of the residual grind.

**What to build:**

Ticket 03 of run-20260909-1501 burned two attempts and the full 80-step budget on an off-by-one in a test the builder session itself had written (`src/model/history.test.ts` comparing `undo()`'s result to `chain[k]` instead of `chain[k-1]`); everything after the first verify failure was spent rewriting the same test to near-identical content, reverting it, and scratchpad-reimplementing the production class. The gap is structural: nothing re-derives the test from the one artifact the model did not author — the plan's origin prompt, already persisted verbatim as `origin.json`'s `prompt` by `writePlanOrigin`. This ticket builds the reconciliation path plus the mechanical guardrails that stop the budget burn and the checkpoint jump-ahead observed in the same run.

1. Attribution — `authoredPathsInFailure(output: string, authoredPaths: string[]): string[]` in a new `src/reconcile.ts`. Extract path-like tokens from the (already compressed) verify-failure output — candidates matching `[\w./-]+\.[A-Za-z0-9]+`, `:line` / `:line:col` suffixes stripped — and return the deduped intersection with `authoredPaths`, in first-appearance order. It never decides what a "test file" is (technology-agnostic; the failure output itself names the files); it answers only "which files this phase authored does the failure name". The call site computes the authored set with existing plumbing: `changedPathsFromDiff(await git.workingDiff(state.cwd))` (`src/reviewer.ts`, `src/git.ts`) — the uncommitted working diff is exactly the current ticket's authored set at verify time, in both classic and session-builder modes.

2. The reconciliation phase — same module, pure half plus I/O half:
   - `buildReconcilePrompt(opts: { spec; ticketNumber; title; criteria; failureOutput; authoredFailing; diff }): string` — a fresh arbiter whose ONLY ground truth is the spec verbatim (from `readPlanOrigin(state.tickets_dir)?.prompt`, `src/plan-identity.ts`; the ticket's title and criteria ride along explicitly labeled as a paraphrase that may itself be wrong). State the failure shape outright: "the implementation may be correct and the test wrong — an off-by-one in a walk/index loop, a terminal sentinel asserted as a failure, a fixture disagreement. Reconcile the test against the SPEC, not against the paraphrase." Output contract: exactly one verdict marker `$RECONCILE_IMPL` / `$RECONCILE_TEST` / `$RECONCILE_INCONCLUSIVE`, numbered findings, then — only under `$RECONCILE_TEST` — one fenced block per corrected file, the reply's final line being `$RECONCILE_END`:
     ```
     === FILE: src/model/history.test.ts ===
     <the entire corrected file>
     === END FILE ===
     ```
     The model NEVER edits the repo: it emits, the railhead applies. That makes the fix mechanically perimetred, logged, and diffable in one stroke.
   - `parseReconcileVerdict(text): { verdict: "impl" | "test" | "inconclusive"; findings: string[]; edits: { path: string; content: string }[] } | null` — a lossy parser in the `readBlockedBy`/`extractContractsBlock` family: case-insensitive markers, prose-wrapped verdicts tolerated, a truncated FILE block yields empty edits (never a partial file write).
   - `applyReconcileEdits(cwd: string, edits: { path: string; content: string }[], allowedPaths: string[]): { applied: string[]; dropped: string[] }` — writes only edits whose `path` is a member of `authoredFailing`; everything else is dropped and reported. The perimeter is the attribution set: the arbiter can fix the files this ticket's own phase authored and nothing else.
   - `runSpecReconcile(...)` — the I/O half: `executeOpendCode` with a FRESH session (never `--session`), the implement-seat model (`state._models?.implement` — the incident's 27B is decent at fixing a specifically-flagged off-by-one when handed the spec; the fix is the fresh context plus the spec, not a bigger model), `livePrefix: "reconcile"`, `guardMode: "kill"`, `maxSteps: Math.min(RECONCILE_MAX_STEPS, state.config.max_phase_steps)` with `RECONCILE_MAX_STEPS = 25` (bounded by design — this is an arbiter, not an explorer), and `stopAfterMarker` set to a `$RECONCILE_END` regex so the #60 post-verdict loop shape cannot eat the phase (the contract makes that marker the model's last line, so `stopAfterMarker`'s terminal anchoring holds).

3. Wiring — run.ts's shared verify-failure block (`src/run.ts`, the `if (!v.ok)` block after `runVerify`, shared by the classic and session-builder paths), after `summarizeIfNeeded`, BEFORE `advanceRetry` emits its `verify_failed` event:
   - Compute `authoredFailing = authoredPathsInFailure(summarizedBlob, workingDiffPaths)`. When non-empty and `ticket.reconcile` is unset, run the phase (`<NN>-<attempt>-reconcile`) and record `{ verdict, findings, applied }` on a new optional `TicketState.reconcile` field (`src/state.ts`, shaped beside the `ladder_rung`/`last_failure_class` precedent, persisted by `writeState` so a resume never re-spends it — bounded to exactly one reconciliation per ticket per run).
   - Verdict `test` with parsed edits: `applyReconcileEdits`, then re-run `runVerify` once. Green: the round ends as an ordinary green verify with the fix logged (`reconcile <phase>: railhead applied test fixes to <paths> — the spec ruled the test wrong`) and proceeds to smoke/review WITHOUT the `verify_failed` event ever reaching the gate machine — counters untouched, ADR 0006 holds (verify is green at the commit; one commit still records the whole ticket). Still red: the ordinary retry path, with the reconcile findings prepended to the feedback.
   - Verdict `impl`: the ordinary retry path with the findings prepended — a fresh-context ruling saying "the implementation is wrong and the spec says why" is the most actionable feedback a grinding session can get.
   - `inconclusive`, or the runner itself dies: the ordinary retry path, the one-shot flag still spent.
   - Blame-aware feedback (issue remedy 6): whenever `authoredFailing` is non-empty — whether the reconciliation ran, ruled, or failed to parse — that round's feedback (the `advanceRetry` feedback string, which also flows into `buildBuilderFindingsPrompt` as the `GateFeedback` findings) gains a preamble: the failing files this phase authored are candidates for a TEST bug (an off-by-one in a walk loop, a terminal sentinel asserted as a failure, a wrong fixture), and the spec — not the session's own assumption — is the arbiter. The preamble names the files; it does not quote the whole spec (the failing session has already burned its context getting here; the spec goes to the fresh arbiter instead).

4. Non-convergent-edit blast radius — `src/executor.ts`. The executor already kills on `spinLoopThreshold` consecutive identical ERRORED tool calls (`toolErrorSignature`); the incident's grind was successful-but-identical REWRITES. Add `writePayloadOf(line): { path: string; content: string } | null` (a completed `tool_use` event whose `state.input` carries a file path and a full replacement content — opencode's write/edit tool family; that is the driver's tool contract, not a project-language assumption) and track a per-path streak: on each completed write to path P, compare `content.replace(/\s+/g, " ").trim()` against the stored normalized content — equal increments the streak, different resets it to 1 (progress is never penalized). Bash/read calls do NOT reset the streak — the `git checkout`-then-rewrite-verbatim shape from the incident is precisely the loop signature. At `EDIT_LOOP_THRESHOLD = 3` near-identical rewrites of one path, kill with the existing `spin_loop` status (no new `ExecStatus` rippling through the failure ladder) and an errorMessage prefixed `non-convergent edit loop: N near-identical rewrites of <path>`; `describeExecFailure`'s spin branch renders that message distinctly. Retry semantics are deliberately unchanged (ADR 0023 — a retry is a probe): with mechanic 3 in place the correction arrives at the FIRST verify failure, before the grind; this cap only bounds the residual.

5. Product-mode prompt shape — stop pre-listing the whole remaining queue (issue remedy 7; the checkpoint-drift invitation). In `runBuilderStep` (`src/run.ts`), compose `buildBuilderPrompt`/`buildBuilderFindingsPrompt` from the CURRENT ticket only, when `directiveGranularity === "product"` and the unit holds more than one ticket; `checkpointTarget(unit)` (the expected marker) still derives from the full unit. In `src/builder.ts`: `checkpointDirective`'s product cadence stops enumerating all ticket names and instead states that the railhead surfaces tickets one at a time and hands over the next after each green checkpoint — never start work the railhead has not surfaced; and `buildBuilderPrompt`'s closing line ("The list above is the forward plan…") adapts to the single-ticket shape ("this is the current ticket; later tickets exist and will be surfaced after its green checkpoint"). The marker-mismatch reconcile in `runBuilderStep` is unchanged — this removes the invitation, not the gate's backstop.

6. ADR — `docs/adr/0032-spec-anchored-test-reconciliation.md`: the human plan origin (`prompt`) is the only anchor no model phase in the run shares; the arbiter is a fresh context; its writes are railhead-applied, perimetred to the ticket's own authored failing files, and bounded to once per ticket per run; and this is the recorded, deliberate exception to ADR 0022's corrections-in-context (the session that wrote the test is exactly the context that cannot see its error — the ruling rides back into the session as findings feedback). Cite run-20260909-1501 ticket 03 as the motivating incident.

Non-goals (deliberate; separate tickets if earned): an independent TDD test-author phase for product mode (issue remedy 2 — a run-shape change needing its own head-to-head; the issue itself says it is not a fix on its own); an assertion-level do-not-weaken diff (remedy 3's full form — mechanically comparing "what a test asserts" is an open design question; the railhead-applied reconcile edits are logged and diffable, which is the cheap half); any new failure-ladder class for the edit-loop verdict (the message prefix is routable; a class split is not earned by the incident).
