- Narrative/theme: The arcade classic, stripped to its essentials and executed cleanly — a vivid snake gliding over a dark board, one piece of food pulsing ahead, score always visible. ## Art direction
Dark-arcade look with strong value separation. Palette roles: background deep charcoal `#14181F` with a subtle two-tone checker (`#171C24`) for depth; playfield border `#2A3240`; snake body saturated green `#3ECF5A` in alternating segment shades (`#35B84E`) so length reads at a glance, head lighter `#6FF08A` with a 1-px dark outline and two darker eye pixels; food warm red `#FF5A4E` with a brighter core `#FF8A7A`, pulsing ±15% brightness on a 0.8 s sine; HUD band `#0E1116` with score in off-white `#E8ECF2`; game-over overlay 70% black scrim with off-white text and green accent on the restart hint. Value bands: background < 20% luminance, actors > 55%, text > 85% — every band clearly separable. Lighting is flat/unlit (2D grid game) with one fake highlight: each snake segment gets a 2-px top-left lighter edge, attenuating to flat on the tail's last segment. What moves: snake steps discretely on the grid (no interpolation, snappy), food pulse and death flash ease with smoothstep; death flash = two 120 ms white pulses on the snake before the overlay fades in over 200 ms.

## Architecture intent (the planner's structural plan)
Spec: \"a complete snake game in rust in a native window\". Tech stack: Rust (single Cargo package); one third-party capability — native window + keyboard events + RGBA framebuffer present — resolved by the scaffold ticket and recorded in DECISIONS.md; tests via built-in `cargo test`. Global constraints: logical grid 24x24 cells, 24 px/cell, origin top-left, +y down; canvas 576x640 px (64 px HUD on top); fixed-timestep sim (60 Hz accumulator, snake step interval shrinks 8→3 ticks with score); seeded RNG injected into the core for deterministic tests; all visual constants only via `src/ui/theme.rs::TOKENS`. Module map: `core` (deep pure-logic module: `Grid`, `Snake`, `Food`, `Game` façade — `new/queue_direction/tick/state/score/restart` — plus `TickEvents`; owns every rule and is exhaustively unit-tested), `render` (pure RGBA rasterizer from `&Game` + time; owns checker background, cell sprites, 3x5 bitmap score font, game-over overlay), `ui/theme` (`TOKENS`), `shell` + `main.rs` (the sole platform seam: window, event loop, key mapping for arrows/WASD/R/Esc, accumulator, present; entry point owned from scaffold, later modules dock into it — no end-of-project integration step). Data flow: key event → shell → core input queue → `tick()` → `TickEvents` + state → `render` → framebuffer → present, strictly one-way. Decomposition rationale: a deep, headlessly testable core keeps all game rules in one place with a tiny interface; the shallow shell isolates the only uncertain dependency; ordering scaffold → core → render/theme → shell wiring → polish means every phase lands green under `cargo build && cargo test` and the real-binary smoke run.

## Giving up honestly (the blocked exit)
If this ticket cannot be completed or its criteria cannot be verified with the tools this session has, do NOT keep retrying the same approach. A live or interactive criterion gets at most 3 attempts, each changing the mechanism or hypothesis; after that, stop. End your reply with exactly one line:

$BLOCKED ticket=<number> kind=<verification-unavailable|implementation-stuck|plan-defect> reason=<the criterion and why it cannot be met, and what you tried>

Kinds:
- verification-unavailable — the work is done to your knowledge and build/tests pass, but THIS seat cannot prove the criterion. Example: a criterion only a viewer can check and you have no working screenshot path (a canvas with no state hook whose pixel-sampling bot cannot finish). The railhead still runs its verify, smoke, and review gates before committing; if they pass it commits, records the criterion as unverified, and routes it to the reviewing seat that can check it. Do not use this kind to avoid work — the gates still decide the commit.
- implementation-stuck — the behaviour does not work and you cannot make it work (failing tests you cannot fix, a bug that resists your attempts).
- plan-defect — the ticket or plan is impossible or self-contradictory as written (a required symbol another ticket owns, an ordering that cannot hold).

A block is neither failure nor a checkpoint: the railhead routes it by kind (verification debt, one corrective attempt, or a replan). Never emit `$CHECKPOINT` for a criterion you did not meet — a false checkpoint is a review finding, and the review will see it. Blocking honestly is always cheaper than thrashing.
