# Replan remaining frontier from checkpoint findings

## Context

ADR 0019 (goal review) and ADR 0017 (structural review) established
checkpoint-level review seats that produce findings. When findings indicate
a plan-level flaw (the original plan assumed something that turned out to
be wrong), the remaining uncommitted tickets were planned against wrong
assumptions and should be **regenerated**, not merely appended to with
corrective tickets.

Before this ADR, the railhead had two responses to checkpoint findings:

1. **Corrective tickets** (goal review): local fixes for implementation gaps.
   Each `[BLOCKER]` finding becomes a new ticket that blocks uncommitted work.

2. **Refactoring tickets** (structural review): structural fixes for drift.
   Each `[BLOCKER]` finding becomes a new `testable: true` ticket.

Neither response handles the case where the **plan itself** was wrong. If the
planner assumed a flat data model and the goal reviewer discovers the project
needs a layered repository pattern, appending a corrective ticket doesn't fix
the remaining tickets that still assume the flat model. The remaining frontier
must be regenerated.

## Decision

Add a **replan operation** (`src/gates/replan.ts`) that re-invokes the planner
mid-run to regenerate only the uncommitted frontier, preserving all committed
work.

### Trigger: `classifyFindings`

A pure function that distinguishes:

- **Implementation gap** → no replan; corrective/refactor tickets suffice.
  Examples: "crashes on null input", "missing error handling", "naming
  inconsistency".
- **Plan-level flaw** → replan. Examples: "plan assumption was wrong",
  "actual architecture diverged from the plan", "remaining tickets reference
  modules that don't exist".

The classifier is conservative: it only triggers replan when findings
explicitly signal a plan-level problem. A single missing feature never
triggers a replan.

### Preservation invariants

- **Committed tickets**: preserved exactly — their files on disk are not
  touched, their `TicketState` entries are byte-identical before and after.
- **Run id/branch/config**: unchanged. The replan is a mid-run operation,
  not a new run.
- **Skipped/failed tickets**: preserved as audit trail.

### Replacement scope

- **Ready/in_progress tickets**: removed from state and their `.md` files
  deleted from disk. These are the old frontier being replaced.
- **New tickets**: generated by re-invoking the planner with
  `buildReplanPrompt`, which gives the planner the original prompt, the
  checkpoint findings, the contracts index, the digest, and the committed
  ticket list as fixed context. The new tickets continue the numbering
  sequence from the last committed ticket.

### The contracts index as the seam

The contracts index (`railhead.contracts.json`, ADR 0008) is what makes
O(ticket) replanning possible. The replan prompt includes a contracts
summary so the planner knows what interfaces already exist — the regenerated
tickets must `reference` existing contracts, not re-declare them. Without
this seam, the planner would have to re-read the entire codebase to
understand what's been built.

### Why not just re-run `railhead plan`?

`runPlan` is destructive: `writeTickets` clears stale `.md` files from the
output directory. Calling it mid-run would delete committed ticket files —
the audit trail of what was built. `replanFromCheckpoint` uses an
append-only write path (direct `mkdir + writeFile`, same as
`writeCorrectiveTickets`) and removes only the old uncommitted `.md` files.

## Consequences

- One additional planner LLM call when `classifyFindings` triggers. Paid
  only when findings indicate a plan-level flaw — most checkpoints won't
  trigger replan.
- The regenerated frontier may have different ticket titles, structures,
  and dependency edges than the original. This is the point — the old
  plan was wrong.
- `meldReplannedTickets` is pure and tested: committed/skipped/failed
  tickets are preserved, ready/in_progress are replaced.
- The run loop resumes from the replanned state via `writeState` +
  `frontier()` — the same path it always uses.
