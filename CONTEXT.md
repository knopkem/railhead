# Railhead

Turn a broken-out plan into hours-long, unattended, sequentially-verified, reviewed-and-committed builds by driving `opencode` over a queue of small-context tickets. It exists because a plan can exceed any one context window — local or cloud — so a plan is sliced into tickets that run one at a time in a single durable session, each one checked before it commits.

## Language

**Railhead**: this tool. Manages a Run over a set of Tickets. This repository.
_Avoid_: foreman, runner, orchestrator

**Plan**: the phase-1 human artifact; a sectioned spec of what will be built (`PLAN.md`, composed from the design and architecture blocks and the ticket breakdown). Produced through an interactive session, not by the Railhead.
_Avoid_: spec, design doc

**Ticket**: one unit of work — a vertical slice with a body, acceptance criteria, and optional `group`/`open_ended` markers, and a life-cycle status. Rendered as one markdown file by `to-tickets`, consumed by the Railhead. A Ticket is a checkpoint, not a dependency-graph node; the emitted array order is the execution order.
_Avoid_: task, story, issue, card

**Corrective Ticket**: a Ticket generated by the Railhead (not the planner) when a Visual Reviewer or goal review fails with [BLOCKER] findings — one per finding, continuing the existing number sequence, inserted immediately before the remaining planned frontier, and processed through the full Gate inline before the originating review may pass.
_Avoid_: fix ticket, follow-up

**Probe**: a deterministic re-check materialized for a confirmed finding — a shell command plus the substring its output must contain when the behavior holds — registered per group under `.railhead/probes/` (persisted in `state.probes`) so later goal rounds re-run it instead of re-deriving the finding by hand. Never a test framework; language-agnostic by construction.
_Avoid_: test, check script

**Run**: one execution of the Railhead over a set of Tickets, in plan order, on a single branch. Identified by a `run_id`.
_Avoid_: job, build, session

**Ledger**: the durable per-Run record of what happened: `state.json` plus one append-only `events.jsonl` per Ticket phase (the `opencode run --format json` stream, verbatim). This is the audit trail and the resume source.
_Avoid_: database, log store, state file

**Stop** (graceful): the operator-initiated Ctrl-C request (ADR 0037). The first press finishes the Ticket in flight's Gate and stops at the commit boundary, so `railhead resume` continues at the next Ticket with no work redone and no Gate owed; a second press is the immediate kill. Distinct from the Halt — a Stop expects no human review, a Halt does.
_Avoid_: cancel, interrupt, abort

**Halt**: the agent-initiated stop signal. Any phase can write `.railhead/STOP` (contents = the reason) to stop the whole Run and ask for a human before more work stacks. An honest-stop control (`status: "stopped"`, ADR 0003), never a failure: the Railhead kills the child at the next stream line, records the reason, and `railhead resume` refuses until the operator deletes the file. Distinct from the Goal Reviewer's `$REPLAN` (ADR 0019) — `$REPLAN` says "fix the plan"; the halt says "a human must look first."
_Avoid_: abort, kill-switch, cancel

**Frontier**: the next Ticket eligible to begin — the first `ready` Ticket in plan order.
_Avoid_: ready set, queue head

**Gate**: the verification-and-review sequence a Ticket must pass to be Committed.
_Avoid_: check, CI exit, approval

**Committed**: the life-cycle status of a Ticket once it has passed its Gate and been recorded as one git commit.

**Builder**: the durable `opencode` session that writes the code, resumed across ticket checkpoints and across gate cycles. It is the only implementer (ADR 0047); corrections arrive in-session as gate findings, so they never cross a context boundary.
_Avoid_: implementer, executor

**Reviewer**: the read-only opencode run invoked to critique a Ticket's diff after verification. Its findings feed back into the Builder's session. Defaults to the same model as the Builder; configurable per `railhead.json`.
_Avoid_: auditor, inspector, critic

**Learning**: a tooling or environment fact extracted from a Builder retry transcript or a Visual Reviewer transcript (e.g. "screencapture -x gives raw PNG on macOS", "cargo run panics without a TTY on this project"). Written by the Railhead (not the agent) to `.railhead/learnings.md` and injected into every subsequent Builder/Reviewer/Visual Reviewer prompt. Per-project, not per-run; capped at ~2,200 chars. See ADR 0012.
_Avoid_: memory, note, fact

**Charter** (a.k.a. Coherence Charter): the terse, normative, cross-ticket visual design contract authored by the planner at plan time (a `## Coherence contract` subsection of the `$DESIGN` block), persisted as `docs/coherence.md`. Three fixed sections — Visual tokens, Layout model, Chrome rules. Surface Tickets are told to honor it exactly rather than invent their own chrome; the Goal Reviewer revises it via `CHARTER:` markers (ADR 0028).
_Avoid_: style guide, design system

**Product arc**: the durable overview a product is built across (`docs/product.md`, ADR 0051) — the decided vision, workflows, traits, stack, and an ordered Roadmap of Steps. Authored/steered via `railhead product` (one condense call, then the planning interview sharpens it, explicit adoption of the full prose); hand-editable; railhead owns the format like the ticket format. Formats the goal for every feature run; the coherence charter, contracts index, learnings, and digest carry the rest of the cross-run consistency.
_Avoid_: roadmap file, backlog, product spec

**Roadmap Step**: one feature-sized increment of the Product arc, `todo → built (run id) → done`; reopened as `todo` with human feedback that the next attempt folds in. Doc order is the execution order, like Tickets; the frontier is strict — a `built` step blocks the steps after it until the human marks it `done` or reopens it (`--step N` overrides with a warning).
_Avoid_: milestone, epic, item

**Feature Run**: one Run whose plan builds exactly ONE Roadmap Step into the existing product (`railhead feature`, plan mode `feature`). Unattended like a build, then stops: the human tests the outcome and steers (the interactive CLI asks done / leave / reopen-with-feedback). Its plan docs live in the run's `.scratch/step-<NN>-<title>/docs` namespace (`state.docs_dir`, stable across reopen attempts); the step identity is persisted (`origin.json`/`state.arc_step`) so `resume`/`run` finish the arc transaction, and the `built` update commits on the run branch. The red-baseline rule (verify must be green before it starts) and the existing-repo planner posture hold; a feature plan's `$VERIFY` copies the project's suite, never extends the global gate. A one-off `railhead feature "<desc>"` bypasses the arc.
_Avoid_: incremental build, sprint
