# src/plan — plan production

Turns a description into the ordered ticket queue: the `runPlan` two-call flow, the lossy plan parsers, the sharpen interview, and plan identity.

## Seams

- `planner.ts` — `runPlan`: one call for a fix; design → ticket decomposition for a build, with an optional post-plan interview, an interactive PLAN.md review, a plan gate, and the deterministic test-hardener ticket around it. Feature mode (ADR 0051/0052) selects `planFeature*` prompts, injects the arc brief + held charter, scopes art direction to new surfaces only, resolves the roadmap step (`arcStepNumber`) for the gate and origin, and writes plan docs into a stable `slug` namespace. Also `runProductSession` (arc condense + optional `refine` interview pass, never writes — adoption is the CLI's) and `deriveFeaturePrompt` (roadmap step → structured feature prompt, grounded in contracts/digest/learnings and a reopened step's prior report), both one stage call through the shared `plannerStage`. Also `runSharpenSession` and `maybeGenerateAgentsMd` (writes a MINIMAL root AGENTS.md for the target project, only when none exists).
- `plan.ts` — prompt builders and the lossy block parsers: `planDesignSystemPrompt`, `planTicketsSystemPrompt`, `planFeatureDesignSystemPrompt`/`planFeatureTicketsSystemPrompt`, `planFixSystemPrompt`, `planContinuationSystemPrompt`, `buildProductSessionPrompt`/`buildProductRevisionPrompt`/`parseProductReply`, `buildFeatureStepPrompt`/`parseFeatureStepReply`, `buildPlanGatePrompt` (feature mode takes `productBrief` + `arcStep`), `parsePlanGateVerdict`, `parsePlanJson`, `parseVerifyBlock`, `parseSmokeBlock`, `parseDesignBlock`, `parseArchitectureBlock`, `parseInterfaceBlock`, `splitCoherenceContract`.
- `sharpen.ts` — the plan-time interview: round parsing, depth budget, `renderPlanInterviewAnswers`, glossary/ADR writes (`appendContextTerms`, `writeGrillAdr`). Modes: `build`, `fix`, `product` (arc sharpening).
- `plan-identity.ts` — `origin.json` (with `base_sha` for history-scoped ticket pre-marking and `arc_step` for feature runs); `checkPlanOrigin` refuses to resume a plan against a changed prompt.
- `plan-contradiction.ts` — detects a resolver failure that contradicts a plan-authored artifact name.

## Invariants

- Planning is exactly two model calls for a build (design, then tickets) and one for a fix. There is no model coverage audit, no plan-repair round, and no `$PLAN` block: the ticket decomposition is validated deterministically (non-empty `what`, criteria present unless `open_ended`) and a truncated decomposition gets exactly ONE "emit the remaining tickets" continuation call. The product-arc session is one condense call plus, when the operator runs the interview, exactly one `$PRODUCT` revision call; the feature derivation is ONE call.
- Feature plans (ADR 0051/0052) plan INTO an existing product: no scaffold-first or entry-point-once rules — the first ticket is an integration slice leaving the EXISTING verify suite green; the feature spine replaces the whole-app launcher spine; the arc brief and held charter are DECIDED context, never re-decided. A held charter scopes art direction to the feature's new surface (no whole-look craft ticket, no false missing-charter warning), and the feature `$VERIFY` copies the project's suite instead of extending the global gate.
- Unattended builds then run ONE plan gate (goal seat, ADR 0049 amendment): it walks the goal's demands against the ticket ownership map and fails/regenerates the frontier via the mid-run replan prompt, capped by `max_replans`; a plan still failing at the cap is rejected before the first commit. Interactive runs skip it (the human review is the coverage check).
- Criteria are observable behaviours (ADR 0007 amendment), optionally with an indented `probe:` recipe inside the same string. The planner never emits "(test)" asks; when the plan's verify block names a test runner, a final hardener ticket is appended after the frontier to transcribe confirmed probe behaviours into the project's own test stack.
- The parsers are deliberately tolerant of mid-array garbage, truncation, and prose-wrapped JSON; tests assert the malformed shapes, not just the happy path. A region whose `"title"` keys outnumber its parsed tickets reports `unparsed` — truncation is never a silent shrink.
- Ticket format coupling (ADR 0007): changes to `src/core/ticket.ts` (the ticket shape or `numberTickets`) require matching prompt/parser changes here.
- Model rounds go through `src/execute/executor.ts` — planning is a client of execute, never the other way around.
